Developer documentation

One API. A world of stories.

Request bodies, parameters, lifecycle states and response examples for Dozy’s mobile contracts.

Implementation status. GET /hello, GET /places and PUT /places/{id} are implemented. The other 10 operations document proposed mobile/backend integration. This page makes no requests and does not execute generation or payments.

Before making a request

  • Paths are relative to the configured base URL; no version prefix is assumed.
  • Every proposed feature request sends X-Installation-Id: <UUID>. Persist the client-generated UUID. There are no accounts or separate installation secrets at this stage. This new shared header still needs mobile implementation.
  • The UUID partitions data; it is not strong authentication. Losing it means no defined library recovery. /hello does not require the header.
  • Send Content-Type: application/json for JSON bodies. Successful JSON responses use the same media type; 201/204 acknowledgements shown with no body do not require JSON.
  • Errors use {"code":"..."}. Place error codes are implemented as documented below. Character/avatar error-code examples remain proposals. Story codes follow the mobile contract.
  • Proposed feature endpoints may return 400 INVALID_INSTALLATION_ID, 429 RATE_LIMITED, or 503 UNAVAILABLE. Additional transport/server failures are possible; lists below are documented cases, not an exhaustive guarantee. 401 UNAUTHORIZED is reserved for future authentication, not current UUID validation.
  • Job status FAILED is a successful HTTP observation (200), distinct from a failed HTTP request. Saved images use durable HTTPS URLs without API authentication.
