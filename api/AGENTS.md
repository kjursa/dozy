# API library guidance

- Keep `contracts` transport-only and independent of Ktor, domain models, databases, and mobile UI. `client` owns HTTP communication; consumers own the HttpClient, engine, and platform identity storage.
- Expose each feature through a plural version container, such as `DozyClient.places: PlacesClients`. Expose containers as public interfaces with internal implementations receiving version clients through constructors. Containers expose `v1`, later `v2`, etc. Inject the feature container into repositories so calls can explicitly select versions per operation.
- Keep singular client interfaces in `client.<feature>.v1` and DTOs in `contracts.v1.<feature>`. Reuse names across version packages; use import aliases when combining them. Bind implementations to their versioned HTTP paths, without a global version selector. Add only implemented versions and operations.
- Keep wire error codes, validation field names, reasons, and allowed field/reason combinations in `contracts` (see `PlacesSaveError` for flat Places errors, and `CharactersSaveError` for typed validation with flat wire codes). Backend emits contract values; client decodes those definitions without duplicating literals, enums or business-error models. Share serializable business-error types between backend responses and client results; keep forward-compatible code lookup/Unknown decoding in the contract serializer (see Places). Keep envelope strings for forward-compatible `Unknown` handling.
- Give error codes unambiguous meanings. Map business details by body code; follow the feature’s documented HTTP failure classification.
- Declare every operation abstract in production client interfaces. Keep fakes in test sources. Map known API errors to typed values and unfamiliar error envelopes to `Unknown`. Follow README.md for each feature’s result/exception contract; always propagate cancellation.
- Test wire shapes and client behavior with unit tests/MockEngine. Run `./test-all` from the repository root; it includes API JVM tests, backend tests, and mobile tests. See README.md for build coordinates and compatibility rules.

- For new or migrated clients, expose an operation-specific sealed result (`Success`, `ApiError`, `TechnicalError`), as in `PlacesListResult`/`PlacesSaveResult`. Keep the shared `TechnicalError` in `api/client`, with `Server(status)` and `Communication(exception)`; transport exceptions do not belong in `contracts`.
- At every public suspend client-operation boundary, include local argument checks, identity lookup, request construction, HTTP execution and decoding inside the result boundary. Rethrow `CancellationException`; map every other `Exception`, including argument/programming exceptions, to `TechnicalError.Communication`. Do not catch `Throwable` or fatal errors. Consumers should not need try/catch for client Exceptions. Classify 5xx as `TechnicalError.Server` before parsing, and decoded business failures as `ApiError`; unknown wire codes remain operation-specific `Unknown`. All clients use flat contract-owned validation codes and shared serializable operation errors. Backend sends contract error objects; client decodes them directly. Keep transport exception/result helpers in the client and reuse `ClientTransport` rather than repeating HTTP classification.
